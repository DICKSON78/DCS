Base URL: https://api.dcs.co.tz/v1 · JSON over HTTPS · one API key per tenant (bank/MNO)

    1. Authentication
Every request requires mutual TLS plus a per-tenant API key in the X-Tenant-Key header. State-changing requests (transaction validation, dispute actions) also require a client-generated X-Request-Id for idempotency — retried requests with the same id return the original result instead of double-processing.

    2. Recipient verification
Most money lost by ordinary customers isn't sophisticated fraud — it's sending to the wrong number by mistake. Before a transfer is submitted, the bank/MNO app calls this endpoint with the recipient's account/phone number and shows the customer the real registered name to confirm (the same pattern mobile money apps already use for "confirm recipient"). This runs before the transaction validation below, and catches wrong-number mistakes at the point the customer can still cancel — which is most of what "fraud detection" means to an everyday user.
POST /v1/recipients/verify

    4. POST /v1/transactions/validate
The core endpoint. Called synchronously at authorization time, before funds move. Budget: p95 < 150ms, p99 < 300ms; breach triggers the tenant's configured fail-open/fail-closed policy.

Behavioural anomaly advisory
The AI agent keeps a rolling behavioural baseline per customer (typical amount, typical recipients, typical time of day). When a transaction is far outside that customer's own normal pattern — e.g. someone who usually sends under TZS 100,000 suddenly sends TZS 250,000 — the risk isn't necessarily high enough to hold or freeze the funds, but the customer should still get a chance to double-check what they're doing. In that case the decision is warn: the transaction is allowed to proceed, but the response carries an advisory object with a plain-language message the bank/MNO app shows the customer before they confirm — a soft "are you sure?" prompt rather than a block.

    6. Webhooks
Registered once via POST /v1/webhooks/subscribe. DCS retries failed deliveries with exponential backoff for 24h.

    8. Rate limits & SLA
        ◦ Default: 200 requests/second per tenant, burstable to 400 for 10s
        ◦ p95 < 150ms, p99 < 300ms on /v1/transactions/validate; breach triggers configured fail-open/fail-closed behaviour
        ◦ Sandbox environment mirrors production limits at 10% quota for pre-production conformance testing
